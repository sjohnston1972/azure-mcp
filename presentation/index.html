The problem

Bicep is great. CloudFormation is great. But neither was designed for a human to talk to — and neither was designed to stay alive after the resources are deployed.

"Just give me a small lab"

The reality: 200+ lines of YAML or Bicep, a fight with the schema, a portal tab open in the background to copy resource IDs. Architects shouldn't be transcribing JSON.

What did I actually deploy?

After two iterations and a rename, you have no clean way to find your own resources, no way to tear down just this deployment, no canvas of what's running. Cloud consoles forget you the moment you log out.

"Spin it up at 9, kill it at 6"

Demo labs, training environments, weekend builds — they want a schedule. Today that means a runbook, a pipeline, a service account, and an evening of YAML. It shouldn't.

The workspace

One screen. Everything in flight.

A two-pane workspace fronted by a collapsible left rail. Designed to live on a monitor all day, not be opened-and-closed.

  • Topology canvas. React Flow with dagre auto-layout. Click a node to see live cloud-API data for that resource.
  • Streaming chat. Token-by-token Claude responses with inline, collapsible tool-call blocks.
  • Project rail. Topologies, deployment history, saved templates, scheduler — all one click away.

Build stage
build · vigil-lab

Claude proposes. The canvas catches up.

Every response is parsed mid-stream for structured markers. Topology, Bicep template, and clarifying answers all render in real-time as Claude reasons through the design.

  • Structured markers. <topology>, <bicep>, <answers> — stripped from chat, hydrated into canvas + drawer.
  • Pre-validation. A custom validate_bicep tool catches syntax errors before the human ever sees the drawer.
  • State survives reload. Per-topology build state in localStorage; Claude's last proposal isn't lost.
Push stage

One click. Live deployment.

A custom deploy_bicep tool spawns Microsoft's official azure-cli container with your service principal, runs az deployment, and pipes every line back to the chat as it happens.

  • Tags enforced post-deploy. Every resource gets mcp-project and mcp-topology-id tags via az tag update --operation Merge. Bicep can forget them; we still find every resource.
  • Status flips on the canvas. Each node moves pending → deploying → success as Azure confirms it.
  • Cleanup is precise. Per-topology Destroy filters by both tags. Project-wide tear-down filters by project only.

Live activity

Always tell the operator what the agent is doing.

A live row above the composer surfaces the current operation — calling tool, reasoning, writing — with elapsed time. No more "is it stuck?" moments during long tool chains.

Multi-cloud

Same workflow. Different cloud.

A top-level toggle swaps the entire tool surface — system prompt, MCP server, deployment engine, icon set, theme. Build a stack in Azure. Build the same stack in AWS. Same chat. Same canvas.

Microsoft Azure live

  • MCP server: mcr.microsoft.com/azure-sdk/azure-mcp
  • Templates: Bicep (multi-file, modules, validation)
  • Deploy engine: az deployment sub create
  • VM picker with free-tier highlights
  • OpenAI gotchas baked into the system prompt

Amazon Web Services live

  • MCP server: awslabs/cfn-mcp-server
  • Templates: CloudFormation (YAML / JSON)
  • Deploy engine: aws cloudformation deploy
  • EC2 instance-size picker (free-tier aware)
  • SSM-driven AMI resolution, gotcha-documented
Lifecycle stages

Five stages. Tool-gated.

Every turn happens in one of five explicit stages, told to Claude in a per-request system block (after the cache breakpoint, so changing stage doesn't invalidate the cached prefix).

Build

2

3

4

Teardown

5

Free

Ad-hoc questions outside the lifecycle.

Scheduler

Daily lab spin-up. Nightly tear-down.

Schedules target a saved template. When a cron fires, the same agentic chat loop runs headless against Claude — non-streaming, but the same tools, the same system prompt, the same prompt cache.

  • One execution path. Live chat and cron jobs go through the same loop. No separate "backend-direct" engine to maintain.
  • Five-field UTC cron. node-cron in-process; re-loaded on every schedule CRUD.
  • Per-template idempotence. Templates are the unit of scheduling — versionable, savable, reusable across projects.

Architecture

Five containers. One Docker network.

The backend doesn't talk to the clouds directly. It runs an agentic loop against Claude with two MCP servers and two shell-out custom tools registered as the action surface.
